# Changelog

## Unreleased

- Fix a `ctx.future_action` created in `create` never running. Future slots were positional and reset by every render: the first `ctx.future`, `ctx.stream` or `ctx.future_action` call of the first render took the slot of an action created in `create` (and a render that made no such call dropped it), which cancelled it for good, so `run` silently did nothing. `ctx.future`, `ctx.stream` and `ctx.future_action` called outside render (in `create`) now get slots of their own, which no render replaces or drops: an action lives until its component unmounts and can be kept in the component struct; a future or stream starts once with the `deps` given there. Calls made in `render` stay positional, as before.
  - `FutureAction::run` on an action that a render dropped while its component stayed mounted (the render no longer made the call at its position, or made a different one) still starts nothing, but now logs a `tracing` error naming the component. Running an action of an unmounted component stays silent.
- Add `FutureState::outcome()` and `FutureState::fulfilled_data()`, which report how the latest run ended. A rejected run keeps the previous run's `data` (`FutureState::rejected(error, previous_data)`), so code that read "has `data` and is not pending" as success took a failure after an earlier success for a success. `outcome()` is `Some(Ok(&data))` when the latest run was fulfilled, `Some(Err(&error))` when it was rejected and `None` while idle or pending; `fulfilled_data()` is the data of a fulfilled run only. `data` keeps its meaning, the last value that succeeded, kept while a run is pending and after it fails, so a view can still show it next to the error; the field and the docs now say so. No behaviour change.
- Add `FutureAction::run_if_idle(args) -> bool`, which starts a run only when none is in flight and returns whether it started. `FutureAction::run` cancels and replaces a run in flight (its result is never applied), so a double click on a button wired to `run` aborted the first request; `run_if_idle` leaves it to finish. `run` is unchanged, and its docs now say that it replaces a run in flight.
- Fix an MCP call running after its caller was told it timed out. A call routed to the event loop waits for its reply for 15 s (30 s for `lurq_screenshot`, the requested timeout plus 5 s for `lurq_wait`) and then answers the client with a time-out error, but the call stayed queued and ran whenever the event loop reached it: a click or key the client believed had failed landed later, possibly after the client had moved on. `Tree::drain_mcp_requests` now drops a queued call whose caller stopped waiting (its deadline passed, or its client went away) without running it, and the time-out error says so. A call the event loop has already started is not interrupted. Tool denies, scopes and `set_enabled` are checked as before, when a call runs. No public API change.
- Add `lurq::app::events::input_source()`, `is_synthetic_input()`, `InputSource { Os, Synthetic }` and `with_synthetic_input(f)`, so an app can tell synthetic input from OS input and protect a control as "person only". Synthetic input reaches the same entry points as OS input, so a handler could not tell an MCP click from a real one. While lurq delivers synthetic input, handlers and the callbacks they reach see `InputSource::Synthetic`: every MCP tool call that reaches the event loop (`Tree::drain_mcp_requests`: `lurq_interact`, `lurq_act`, `lurq_set_value` and the rest, and the release of input an MCP client held, also by `Tree::shutdown_mcp`), `synthetic_input::apply`, and a `SyntheticInput` injected on a window (`WindowHandle::inject_input`). Anything else sees `InputSource::Os`. The source is per thread and set only during the delivery. No behaviour change.
- Add `MarkdownProps::fit_content(bool)`: a `Markdown` document sized to its content instead of filling its container, like CSS `width: fit-content; max-width: 100%`, so a chat bubble hugs its message.
  - The document is as wide as its widest block (a short message as its longest line) and never wider than its container, where its text wraps. Paragraphs, headings, lists, quotes and footnotes size to their content; a long list item wraps beside its marker.
  - Every block is then stretched to the document's width, as CSS blocks are: a code block's box and a rule span the widest block. A code block does not wrap: it is as wide as its longest line up to the container's width, and a longer line overflows its box, as when filling. A table still fills the container's width, so that its columns line up across its rows. An explicit `.width(...)` still sets the document's width.
  - A `Row` gives its children unbounded width: a bubble in a row needs `.max_width(Dimension::Pct(100.0))` or a `flex_shrink` factor for its text to wrap at the row's width.
  - Without `fit_content`, a `Markdown` document and its blocks fill their container's width as before. No behaviour change.
- Fix `VirtualizedList::reveal_key` not scrolling a list mounted with the key already set. On the list's first layout the reveal checked its target against row positions built before any row was measured, all at 0. A target among the first 64 rows but below the viewport (row 40 of 200, say) therefore looked visible, and the reveal was dropped without scrolling. The positions are now rebuilt from the heights that layout just measured before the reveal is checked, so the row is scrolled to the top of the viewport within a few frames and without further input. A reveal on a list that has no items yet now waits for them instead of being dropped, so a list mounted before its data loads still opens on the row. A key missing from a non-empty list is still dropped, and an already-visible row still does not move. No public API change.
- Add `Ctx::scroll_into_view(&ElementRef)` and `ElementHandle::scroll_into_view()`, the public way to scroll an element into view: every scroll container around it, innermost first, scrolls by the smallest amount that shows it, on each axis the container scrolls, like the web's `scrollIntoView({ block: "nearest", inline: "nearest" })`. An element already in view moves nothing, and one larger than a viewport is aligned to the viewport start. A `Ctx` request is resolved once the render that attaches the ref is laid out; the last request wins and a ref absent from the tree is ignored, as for `Ctx::focus`. When a request moves a container the pass lays out again, so the frame it draws already shows the element. Inside a `VirtualizedList` this reaches elements of mounted rows; `reveal_key` remains the way to reveal a row that may not be mounted.
  - Behaviour change: `Ctx::focus` and `ElementHandle::focus` (and `TextInputHandle::focus`) now scroll the focused element into view, as Tab and Shift+Tab already did and as a browser's `element.focus()` does. Focus by a pointer click still does not scroll. A component that calls `ctx.focus` in every render reveals the element again in every render.
  - Behaviour change: scrolling focus into view (Tab included) now moves a container only along the axes it scrolls; a `ScrollVertical` whose content is wider than it is no longer scrolled sideways.
- Document row state in `VirtualizedList`: a row outside the viewport and overscan is unmounted and created again from its props, so state the row holds itself (fields from `create`, `ctx.signal`, element refs, a text-input value signal it created, focus) starts over. The rustdoc and the layout guide show keeping such state above the list, keyed by row key, in a signal or store the screen owns and provides to the rows. No public API change.
- Add focus-visible, a keyboard-only focus state like CSS `:focus-visible`, so an app can show a focus ring only for keyboard focus.
  - The tree remembers the modality of the last input that can move focus. Tab and Shift+Tab, and any key press other than a bare modifier (Shift, Control, Alt, AltGraph, Super/Meta) made without Control, Alt or Super/Meta held, make focus visible: a key pressed on a clicked button shows its ring, a shortcut such as Ctrl+C does not. A mouse button press (also one that only closes a popup) and `ElementHandle::click()` hide it. A focus request (`ctx.focus`, `ElementHandle::focus()`) inherits the last input's modality; before any input it is pointer, so focus set at startup shows no ring. A focused text input is always focus-visible, as browsers treat text fields. Synthetic input and MCP `lurq_interact` follow the same rules.
  - `.focus_visible_style(Style)` / `.focus_visible(|style| ...)` on every element: merged over the focused style while focus-visible, under the hovered and active styles.
  - `InteractionState::is_focus_visible()`, `core::ElementRef::focus_visible()` and the reactive `ElementRef::focus_visible_signal()` (also on `ElementRefMut`), and `Tree::focus_visible()` for the focused element. Losing focus clears it.
  - MCP `lurq_read_tree` lists the state as `focus-visible`, `lurq_inspect` reports `"focus_visible": true`, and DevTools shows a node's focus-visible style.
  - Behaviour change: the checkbox box (`box_focused_style`), slider thumb (`thumb_focused_style`) and select trigger (`SelectStyle::trigger_focused`, including its default `BorderFocus` border) focus styles now show only while focus-visible (Tab or a key press, not a click or drag), like a browser's native focus rings. So do the form buttons' `border_focus` and the form checkbox and slider focus borders. Text inputs, including `FormTextInput`, keep their focus border for any focus. For a style on every focus, put `.focused(...)` on the control.
  - `focused_style` / `.focused()`, `ElementRef::focused()` and `focus_signal()` are unchanged: they still apply to any focus.

## 0.42.0 — 2026-10-08

- Add hosted MCP: an app with an MCP server of its own (its own port, token, discovery and settings) can serve lurq's tools from it instead of starting lurq's server.
  - `McpConfig::hosted()` makes `Tree::enable_mcp` start no listener and write no discovery file; `McpHandle::port()` is `0`.

  - Scopes, tool denies, `set_enabled`, event-loop execution through `Tree::drain_mcp_requests` and held input work as with lurq's own server.
- A server started without `hosted()` is unchanged.

## 0.41.3 — 2026-10-07

- Add input held across `lurq_interact` calls, so an MCP client can drive a gesture whose samples arrive one frame apart: dragging a node or a resize handle, a marquee, a slider or scrollbar thumb, a middle-button or space-drag pan (#37). `drag` delivers its move, press, six moves and release inside one call, and `key` its press and release, so the whole gesture landed between two frames and no frame ran while the button was down.
  - `press` (a `ref` or `x`/`y`, and `button`: `left` by default, `middle` or `right`) moves the pointer there and presses the button, which stays down. `release` (`button`, optionally a target to move to first) releases it. `key_down` and `key_up` hold and release a key, with the key names of `key`.
  - A `move` in a window that holds a button or key is a held move: it reaches the tree entry points a real move with the button down reaches, so drags, sliders, scrollbars and text selection follow it and keep the pointer outside their bounds. A call that delivers held input makes the winit shell present right after the drain, before any redraw is requested, as a real mouse-move stream presents from inside its events: one move per call is exactly one rendered pass per move.
  - Held modifier keys apply to every `lurq_interact` action in their window, as real keys that are down do, together with the action's own `modifiers`: a held `Shift`, `Control` or `Alt` sets `shift`, `ctrl` or `alt` on later pointer events (moves, presses, releases, clicks) and key events (`key`, `type`, `key_down`, `key_up`); a held `Meta` or `Super` sets `meta` on key events only, since pointer events have no `meta`. Scroll events carry no modifiers, so `wheel` passes them only to its pointer move.
  - Holds belong to a window and to the MCP session that pressed them: holding needs a session-based connection (protocol 2025-06-18, or another version before 2026-07-28; 2026-07-28 serves requests without sessions and is refused), and any client may release. Releasing a button or key that is not held, pressing a held button again, `key_down` of a held key, and `click`, `double_click`, `drag` or `key` of a held button or key are refused. Each held action's result, and a new `held` field of every window in `lurq_windows`, report what a window holds.
  - Held input never stays down once its client can no longer release it. It is released when the session that holds it ends (the client deletes it, it expires after five minutes without a request, or the server stops), when the window loses focus or closes, and when `lurq_interact` stops being available (MCP disabled, the Interact scope removed or the tool denied). A button ends the way the OS ends a press it takes over (`Tree::mouse_press_taken_by_os`: an up event, no click, and a drag ends without a drop), a key with its up event, and the next `release` or `key_up` says why nothing is held. `Tree::drain_mcp_requests` makes these releases and returns `true` when it made one; `Tree::shutdown_mcp` releases what is still held.
- Fix a held drag keeping the event loop busy: while a scrollbar, slider, text selection or `on_drag_*` drag was held, the winit shell polled its loop without pause and every pass counted as required, so a pointer held still spun a CPU core for as long as the button stayed down (about one core while an MCP client held a drag handle). A held drag changes only on input, and every input that moves it asks for a redraw, so it no longer counts as a tick source: held still, the loop waits and a pass with nothing to draw is skipped. A move during the drag is presented as before.
- Apart from held modifier keys, the other `lurq_interact` actions, and a `move` in a window that holds nothing, are unchanged.
- No public Rust API change.

## 0.41.2 — 2026-10-06

- Fix a long text stopping partway down when scrolled to, with blank space below it, in a multi-line `TextInput` or a wrapped `Text` inside a scroll view or another clip. When a text was taller than its clip and painted at a size its layout had not shaped (a display scale other than 1, for example), lurq shaped it only down to the clip's bottom. If that bottom fell just below the top of a line, the shaped rows ended at that line without one being skipped for the clip, and the cut glyph list was cached as the whole text's. Every later paint of the same text, scrolled or not, drew only those rows, until an edit changed the text. Such a paint is now cached for its clip only.
- Fix MCP discovery files piling up. An app removes its `<pid>.json` discovery file when it shuts down, but an app that was killed (a test process, a crash, a task manager kill) left its file behind, with the port and bearer token of a server that no longer listens; one Windows machine had several hundred. An MCP server now removes, when it starts, every `<pid>.json` in the discovery folder whose process no longer runs, as the operating system reports it (`OpenProcess` on Windows, `kill(pid, 0)` on Unix). Files of running processes, of processes it may not query, and files not named `<pid>.json` stay. Unix builds with the `mcp` feature now depend on `libc`.
- No public API change.

## 0.41.1 — 2026-10-05

- Fix the first full Canvas frame after a font change shaping and uploading almost every label of a large page again. Loading, installing or registering a font, and `set_scale_override`, replace the app's canvas text engine, and 0.41.0 created the new engine's shaped-text cache least recently used within its 8 MiB budget until a GPU renderer ended its first frame. A first frame charged more than the budget evicted its own first texts while drawing it. None of its texts counted as the previous frame's, so each text the next frame shaped again evicted the next one it needed, and that frame missed on nearly the whole page. When a GPU renderer has ended frames of the engine being replaced, the replacement is now framed from its first frame: that frame keeps a page up to the 16 MiB ceiling, as any later frame does, and the next frame shapes nothing again. An engine that no GPU renderer has framed, such as one used only by software canvases, is still replaced by a least recently used one.
- No public API change.

## 0.41.0 — 2026-10-05

- Fix Canvas text and images being shaped and uploaded again every frame once a page drew more of them than the caches held, which made panning and hovering a large page redraw every label from scratch:
  - Shaped text: the 256-entry least-recently-used cache, which missed on every label once a page drew more than 256 distinct texts in the same order each frame, is replaced by a frame-stamped policy with a byte budget (the existing 8 MiB, with 256 bytes charged per entry beyond its text and pixels). Text that the current or the previous frame used is never evicted, and lookups are hashed instead of scanned.
  - Shaped text that stays cached keeps its asset id, so its texture is uploaded once instead of every frame.
  - WGPU and DX12 now share one Canvas asset cache. It never evicts a texture that the current or the previous frame drew. When those two frames alone need more than the budget, it keeps them up to twice the budget; a texture beyond that is drawn but not kept past its encode, so the rest stays resident instead of the overflow being evicted and uploaded again every frame. Once frames need less, it returns to its budget.
  - A frame ends when a GPU renderer encodes, so passes that draw no canvas do not age entries. A replacement presentation drawn in batches over several encodes is one frame, which ends at the encode that commits, aborts or supersedes it, or resizes or detaches its canvas, so a page larger than a budget is not evicted by its own later batches. A pass that only draws retained artwork ages nothing. The completed front and the captured artwork are render targets outside both caches, so eviction never changes what is shown.
- Add `lurq::canvas::CanvasAssetBudget` (`new`, `bytes`, `ceiling_bytes`, `DEFAULT_BYTES` of 64 MiB, `MAX_BYTES` of 1 GiB, and `Default`) and `with_canvas_asset_budget` on `WgpuRenderEngine` and `Dx12RenderEngine` to set a renderer's Canvas asset budget. The shaped-text budget is not configurable.
- Profiler: `CanvasProfile` (`render.canvas.counts`, WGPU and DX12) adds `asset_cache_budget_bytes`, `asset_cache_stretch_bytes` (the most the cache was charged above its budget during the encode), `asset_cache_uncached` and `asset_cache_uncached_bytes` (textures drawn but not kept). `CanvasTextProfile` (`canvas_text.counts`) adds `shape_cache_uncached` and `shape_cache_stretch_bytes`. The JSON export keys are additive.
- Behaviour change: DX12 `asset_upload_details.cache_evictions` now also counts textures evicted while drawing to make room, not only those evicted after the encode, so its counts are not comparable with earlier versions.
- Memory: while the current and the previous frame need it, each cache can settle at up to twice its budget, by default 128 MiB of charged Canvas textures per renderer and 16 MiB of shaped text per app. These are policy charges, not GPU allocation sizes. While a replacement drawn in batches is open, neither cache ages; each stays within its ceiling, and textures it cannot keep are retired at every encode.
- Breaking: `CanvasProfile` and `CanvasTextProfile` have new public fields. Both have only public fields, so code that builds them with a struct literal needs the new fields or `..Default::default()`, and exhaustive patterns need the new fields or `..`.

## 0.40.1 — 2026-10-05

Security fix:

- Fix sensitive text being readable in inspection screenshots. `Text::sensitive()` (0.40.0) was redacted in every MCP and DevTools text surface, but `lurq_screenshot` and DevTools node screenshots captured the window as painted, so any MCP client could read a one-time password from the image. A capture made for an inspector now covers every pixel a sensitive text's glyphs can paint (anti-aliased edges, text shadow and transforms included, limited to its clip) with an opaque grey bar, at the place and size the text has on screen: `lurq_screenshot` of a window, a region or an element (by ref), on every render backend, and a DevTools node screenshot, from the GPU or drawn in software. The `lurq_screenshot` tool description says so.

## 0.40.0 — 2026-10-05

Behaviour changes:

- `WinitWindow::on_size_changed` reports the size the window took, read back from the window, instead of the size a resize requested; it is never called with a minimized window's client area, and is called once per size rather than for every event or request that repeats it. An app that persisted the requested size, or counted calls, sees fewer and real values.
- `WindowHandle::resize` of a minimized window restores the window and applies the size (on Windows it was ignored). A maximized or full-screen window stays in its mode, as before.
- `lurq_resize` takes a maximized or full-screen window out of its mode, answers only once the resize has been applied, with the size the window took, and fails when the window did not take the requested size, has no native window yet, or belongs to a headless tree (it used to answer `"ok": true` at once). Its reply has no `note` field any more.
- An `Enter` marked `KeyboardEvent::composing` no longer submits a form, activates a control, inserts a newline or blurs a text input; `on_key_down` handlers still receive it.

- Fix resizing a minimized window. A window started minimized (`Start-Process -WindowStyle Minimized`) kept its minimized frame (237x39 on one Windows machine), and `lurq_resize` could not bring it back: Windows does not resize a minimized window, yet the tool answered `"ok": true`, `on_size_changed` was told the requested size, and the next state sync read the minimized client area back. Now:
  - Every resize restores a minimized window before requesting the size, the same on Windows and macOS. `WindowHandle::resize` does only that: a maximized or full-screen window stays in its mode, so an app restoring a saved size or fitting its content never takes the user out of full screen. `lurq_resize`, which asks for an exact size, also leaves full screen and maximized, in the order full screen, minimized, maximized (a window minimized from maximized comes back maximized); it is how an agent restores a minimized window.
  - `lurq_resize` answers once the shell has applied the resize, with the client size the window really took and the modes it left (`restored_from`, and `still` for a mode the platform has not finished leaving). When the window did not take the requested size it fails with the real size and why: still minimized, maximized or full screen (macOS animates leaving full screen), or limited by the window's minimum or maximum size or the screen. A window without a native window, and a headless tree, fail at once instead of answering `ok`. Sizes above `u32::MAX` are refused. A call that times out leaves nothing waiting in the window.
  - `lurq_windows` reports `minimized`, `maximized` and `full_screen` for each window.
  - `WinitWindow::on_size_changed` reports the size the window took, read back from the window, rather than the size requested. It is never called with a minimized window's client area, and is called once per size rather than for every event that repeats it.
- Fix an `Enter` passed on during an input method composition submitting a form. 0.39.0 delivers a press other than `Process` that arrives while a composition is shown as usual, marked `KeyboardEvent::composing`, and lurq's own `Enter` handling acted on it: the form of the focused single-line input submitted (with the composition still uncommitted), a single-line input outside a form blurred, and a multi-line input took a newline. An `Enter` marked `composing` still reaches `on_key_down` handlers, but no lurq default acts on it (form submit, button or select activation, newline, blur), as the web's `isComposing` `Enter`; a form, which exposes no key handler, could not guard it itself. Once the composition is committed, `Enter` submits and activates as before.
- Add sensitive text: `Text::sensitive()` draws text that is kept out of inspection, for a one-time password or a secret the user must read on screen. It is laid out, painted and captured as usual, but the MCP tools (`lurq_read_tree`, `lurq_inspect`, the `lurq_find*` lookups, accessible names derived from it) and DevTools (tree, inspector, snapshots) show `•••` in its place, whatever its length, with the attribute `sensitive=true`. Selection follows `selectable` as for any text (off by default). New `lurq::core::Sensitive<T>` holds such a value elsewhere: its `Debug` output and DevTools rendering are `•••`, so it stays out of DevTools' signal values and history and the props inspector; it has no `Display`, and `expose()` returns the value. `lurq::core::REDACTED` is the marker.

## 0.39.0 — 2026-10-04

- Add input method (IME) composition to text inputs, on Windows and macOS alike. Until now the winit shell never let a window's input method compose (winit leaves it off until the app allows it), so Japanese, Chinese and Korean input could not compose in a text input, and lurq had no notion of a key the input method takes: Windows reports one as `Process` with the physical key as its code, so the `Enter` that confirms a composition would have reached `on_key_down` handlers and lurq's defaults as an `Enter`.
  - While a text input that is not masked has focus, the window lets the input method compose (`set_ime_allowed`) and places its candidate window at the input's caret (`set_ime_cursor_area`); other focus, and masked inputs, turn it off.
  - The composition text is shown in the input at the caret, in place of the selection, underlined in the text colour, with the caret at the input method's cursor; the value and `on_input` wait for the commit. A commit inserts the text like typing: `on_input` handlers see a `KeyboardEvent` whose `key` is the committed text and whose new `composing` field is set. A cancelled composition leaves the value; moving focus away cancels it.
  - The keys the input method takes, including the `Enter` that confirms a composition, no longer reach `on_key_down` handlers or lurq's own key handling (newline, form submit, button activation): Windows reports them as presses of `Process` (which never count as an ordinary key), macOS not at all. Their releases reach `on_key_up` handlers with the new `KeyboardEvent::composing` set. Any other press is delivered as usual, with `composing` set while a composition is shown, so a key the input method passes on (a space after a Korean syllable) is not lost and a composition the platform never ends holds no key back; `ImeEvent::Enabled` and a focus change end a composition left behind.
  - New API: `Tree::ime(ImeEvent)` applies `ImeEvent::{Enabled, Preedit { text, cursor }, Commit(text), Disabled}` (`lurq::app::events`) to the focused text input, for custom shells and tests; `Tree::is_composing()`, `Tree::ime_allowed()`, `Tree::ime_cursor_area()` (an `ImeCursorArea` in logical pixels), `TextInputHandle::composition()`, and the `KeyboardEvent::composing` field. The winit shell maps `NamedKey::Process` to the key `"Process"` (it was an empty string).
- Fix a `Select` trigger without a background painting white. A trigger part with no `background` (`SelectStyle::unstyled()`, or a part passed to `SelectStyle::trigger` that sets none) was filled with a fixed white, whatever the theme, so an app that styled the trigger on a dark surface got a white pill under light text. Such a trigger now paints no fill, like a button or text input without a background; its border, radius and shadows paint as before. The default `SelectStyle` still fills the trigger with the theme's `SurfaceInput`, and a part that sets a background is unchanged. Behaviour change: an app that relied on the white needs `.background(...)` on its trigger part.
- Fix checkboxes and sliders falling back to fixed colours where their style set no fill: a white unchecked box, a green checked box, a slate track and thumb, whatever the theme. A checkbox or slider the app has not styled now takes the theme's roles, as the form theme does: the box `SurfaceInput`, the checked box `Accent`, the track `Border`, the thumb `Accent`. A part the app styles without a fill paints none, like the select trigger: `.box_part(...)` or `.checked_box(...)` without `background`, `.track(...)` or `.thumb(...)` without one. A checked box whose `checked_box` part is not set keeps the unchecked part's fill, or the theme's `Accent`. Fills the app sets (including generic `.background()`) are unchanged. Behaviour change: an unstyled checked checkbox is `Accent` rather than green, an unstyled slider `Border`/`Accent` rather than slate, and an app part that relied on a fallback fill needs `.background(...)`.
- Add `Tree::painted_quads()`: what the last layout paints, as `Quad`s in paint order, without a window or render engine, so tests (including an application's, after `Tree::pass_headless`) can check fills, borders and carets the element tree does not show.

## 0.38.0 — 2026-10-04

- Add complete presentation transactions to GPU Canvas, so that an application rebuilding a canvas after a zoom or a document change no longer exposes a blank or partly drawn frame. `Context2D::begin_presentation()` returns a token and records the following drawing batches, over as many frames as they take, into a replacement surface while the previous complete surface stays presented. `commit_presentation(token)` publishes that replacement only if it is still the current one, and `abort_presentation(token)` discards it and keeps the completed front. A new `begin_presentation()` supersedes an unfinished replacement, whose token can no longer publish. Software canvases isolate the replacement in a pixmap.
- Add retained artwork: `capture_artwork()` captures the replacement's artwork before transient overlays, without a CPU readback on GPU backends; `draw_retained_artwork(matrix)` reprojects the last complete artwork through a device-pixel camera matrix inside a presentation; `forget_artwork()` releases it when the document or page changes.
- Snapshots (`CanvasHandle::snapshot`) taken while a replacement is pending return the completed front and its revision.
- When the renderer cannot take another replacement target, the canvas reports the new `CanvasError::PresentationBusy` and keeps the completed front and its revision. Ordinary writes are then refused until a later `begin_presentation()` admits a new replacement; treat it as temporary pressure and retry once in-flight submissions complete.

## 0.24.2 — 2026-09-25

- Fix a UI-thread hang when a callback writes the signal it observes. `Signal::set` and `Signal::update` called the signal's subscribers while holding its value and subscriber locks. So a `ctx.watch` callback that set its own signal never returned, and neither did subscribing to or dropping a subscription of that signal from a callback. A common case was restarting a `FutureAction` from a watch on its own state: the completion set the state, the watch called `run`, and `run` set the state to `Pending`. Cooperative (non-Tokio) futures hung a second time, because `AsyncTask` was polled while holding the task lock that `run` takes. A notification now holds no lock while it calls observers, and the task lock is released before polling.
  - Writes from callbacks follow one rule. The value changes at once, and the notification comes after the current one. Every observer first receives the current value, then all of them are notified again with the latest value. Several writes during one notification produce one more notification. Writes from other threads during a notification are delivered by the thread that is already notifying. A watcher added during a notification starts with the next one. A watcher dropped during a notification is not called again.
  - Effects rerun when they write a signal they read, including during their first run. Before, such writes were missed. An effect never reruns inside its own run.
  - `set` still does not compare values. A callback or effect that writes its own signal on every notification is stopped after 100 consecutive self-caused notifications, and the triggering write panics with the signal or effect id. The signal keeps working afterwards.
  - Inside a `ctx.watch` callback, `update` on the watched signal panics instead of hanging, because the callback still borrows the value. Use `set` there. `update` still works on other signals and from effects and memos.
  - A notification no longer copies the watcher list into a new `Vec`; observer lists are copy-on-write. A signal's value now sits behind an `Arc`, which costs one extra allocation per signal. `set` allocates only when a notification still borrows the old value.
  - The Reactivity guide documents writes from callbacks.

- Add application-defined `Extra` roles to `TypographyStyle`, `RadiusSize`, `SpacingSize`, and `BorderSize`, stored in new `extra` maps on `ThemeTypography`, `ThemeRadii`, `ThemeSpacing`, and `ThemeBorderSizes`. Each role has an `extra(name)` constructor and converts from `&str` and `Arc<str>`; the tables gain `try_get`, `resolve`, and `try_resolve`. Names are interned so these roles stay `Copy`. A missing name follows the palette: table `get`/`resolve` panic, while nodes resolve an unknown radius, spacing, or border size to `0` and an unknown typography variant to the default text style. `Breakpoint` has no extras because `Responsive` orders overrides by the enum.
- Document `PaletteColor::Extra`, the new extras, and font-weight matching in the Theme guide.
- Upgrade cosmic-text from 0.12 to 0.19.0 and swash from 0.1.19 to 0.2.10, the version cosmic-text uses, so lurq's rasterizer and cosmic-text share one swash and one fontdb (0.23, also shared with usvg now). Shaping moves from rustybuzz to harfrust; the development-profile overrides add `harfrust`. The text, input, layout, Markdown, and canvas regression suites pass with unchanged expected values, so measurement, wrapping, caret, and selection geometry match 0.12 for the covered fonts and scripts. Text ending in a line break still ends at that break (cosmic-text 0.19 would add an empty final line). The rasterizer now places variable fonts at the `wght` position cosmic-text shapes them with, so outlines match advances; lurq still requests the matched face's own weight, so variable fonts render as before. The cap-height fallback for fonts without the metric reads the Latin H bounds with skrifa.
- Add letter spacing. `TextStyle::letter_spacing` is extra space after every glyph in logical pixels (negative tightens; default `0.0`); like CSS it applies to spaces and after the last glyph of a line. It scales with the display scale factor like `font_size`, is part of every text cache key, and measurement, wrapping, painting, carets, hit testing, and selection use the spaced advances. `Text::letter_spacing(f32)` overrides the resolved style (typography roles included), `TextInput::letter_spacing(f32)` sets the value and placeholder styles, `MarkdownTextStyle::letter_spacing` and `CanvasFont::letter_spacing` cover Markdown and canvas text. Rich-text spans space in pixels whatever their font size.
- Breaking: `TextStyle`, `MarkdownTextStyle`, and `CanvasFont` struct literals without `..Default::default()` (or `CanvasFont::new`) need `letter_spacing`. `FontWeight::to_cosmic()` and `FontStyle::to_cosmic()` return cosmic-text 0.19 types.
- Breaking: exhaustive matches on `FontWeight`, `TypographyStyle`, `RadiusSize`, `SpacingSize`, and `BorderSize` need the new variants. `ThemeTypography`, `ThemeRadii`, `ThemeSpacing`, and `ThemeBorderSizes` struct literals need `extra` or `..Default::default()`. `ThemeRadii`, `ThemeSpacing`, and `ThemeBorderSizes` are no longer `Copy`.

## 0.20.0 — 2026-09-17

- Add gradient paints to `Context2D` fills and strokes: linear, radial and angular, 2 to 16 stops, with a centre, a size and a rotation normalised to a box. A gradient is a fragment-shader paint — one 256-texel ramp per distinct stop list, and paint coordinates carried in the vertex `uv` solid paths leave unused — so the mesh-cache key and the per-batch vertex charge are unchanged. An unusable gradient draws nothing rather than a colour of its own choosing, and is refused for shaped text with `UnsupportedPaint`.
- Add outer and inner shadows (`set_shadow`) and a `filter`-like layer blur (`set_filter`) to fills, strokes and shaped text. Both are rasterised once on the CPU into a premultiplied image and drawn like any other image, so the software backend and both native backends share one implementation. Bounded by a reduced raster for wide blurs, clipping to the surface, `MAX_EFFECT_PIXELS`, and 512-unit caps on blur and spread; rasterisations are cached process-wide at 32 MiB with random eviction. Offsets, blur and spread are in user space and scale with the transform, unlike HTML Canvas.
- Add eighteen blend modes through `set_global_composite_operation`, and isolated group compositing through `begin_layer(alpha, blend)` / `end_layer`, which is what makes a group of overlapping shapes fade as one image. Layers nest to `MAX_LAYER_DEPTH`, hold their commands on the surface until they close, and cost the renderer two shared tile-sized textures per open depth rather than a surface-sized target.
- Breaking: `fill_style()` and `stroke_style()` return `Paint` instead of `Color`; `Paint::color()` recovers the colour of a solid paint. The setters still accept `Color` and colour strings unchanged.
- Backdrop blur is not included: it reads the surface it writes, and its ordering guarantee is not yet stated. Tracked as lurq#17.
